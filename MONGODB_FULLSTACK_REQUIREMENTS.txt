================================================================================
  1. WHAT IS MONGODB & WHY USE IT
================================================================================

MongoDB is a NoSQL (Not Only SQL) database.
Instead of storing data in TABLES and ROWS like MySQL,
MongoDB stores data as DOCUMENTS (similar to JSON objects).

Example — MySQL stores a product like this:
  Table: products
  | id | name              | brand | price | stock |
  |----|-------------------|-------|-------|-------|
  | 1  | Pro Match Football| Nike  | 2999  | 15    |

  Table: product_sizes (separate table for sizes)
  | id | product_id | size |
  |----|------------|------|
  | 1  | 1          | 3    |
  | 2  | 1          | 4    |
  | 3  | 1          | 5    |

Example — MongoDB stores the SAME product like this (one document):
  Collection: products
  {
    "_id": ObjectId("64abc123..."),
    "name": "Pro Match Football",
    "brand": "Nike",
    "price": 2999,
    "stock": 15,
    "sizes": ["3", "4", "5"],          ← embedded directly!
    "colors": ["White", "Orange"],     ← no separate table needed
    "images": ["url1", "url2"],        ← all in one document
    "description": "Professional football...",
    "category": "football",
    "rating": 4.7,
    "reviews": 312
  }

Why MongoDB is good for SportZone:
  ✅ Product sizes, colors, images all in ONE document (no JOINs needed)
  ✅ Schema is flexible — admin can add new fields without changing DB structure
  ✅ Scales horizontally (add more servers easily)
  ✅ JSON-like documents match JavaScript naturally
  ✅ Very fast for read-heavy applications (e-commerce product browsing)
  ✅ Great for storing varied product data (a football and a bicycle have
     different attributes — MongoDB handles this easily)
  ✅ Spring Boot has excellent MongoDB support via Spring Data MongoDB


================================================================================
  2. MYSQL vs MONGODB — KEY DIFFERENCES
================================================================================

  Feature             MySQL (SQL/Relational)       MongoDB (NoSQL/Document)
  ──────────────────────────────────────────────────────────────────────────────
  Data Format         Tables + Rows                Collections + Documents
  Data Structure      Fixed schema (columns)       Flexible schema (any fields)
  Query Language      SQL                          MongoDB Query Language (MQL)
  Relationships       Foreign Keys + JOINs         Embedded documents / References
  Scaling             Vertical (bigger server)     Horizontal (more servers)
  Transactions        Full ACID transactions        ACID since MongoDB 4.0
  Java Integration    JPA / Hibernate              Spring Data MongoDB
  Repository          JpaRepository                MongoRepository
  ID Type             Long (auto increment)        ObjectId (24-char hex string)
  Schema Changes      ALTER TABLE (painful)        Just add new fields (easy)
  Best For            Complex relationships,        Flexible data, content,
                      financial transactions        catalogs, real-time apps

  For SportZone e-commerce:
    MongoDB is a GREAT choice because:
    - Products have flexible attributes (sizes, colors, specs vary per sport)
    - Cart and wishlist fit naturally as embedded/referenced documents
    - Product catalog reads are very fast
    - Admin adding new product fields requires no schema migration

  4. MONGODB DOCUMENT DESIGN (COLLECTIONS)

MongoDB uses COLLECTIONS (like tables) containing DOCUMENTS (like rows).
Documents are JSON-like objects. Related data is often EMBEDDED inside one
document instead of split into multiple tables.

================================================================================

Step 1: Create Spring Boot project at start.spring.io

      ✅ Spring Security

Step 2: application.properties
  spring.data.mongodb.uri=mongodb://localhost:27017/sportzone_db
  spring.data.mongodb.database=sportzone_db

Step 3: That's it! Spring Data MongoDB auto-configures everything.

No need to:
  ❌ Create tables manually
  ❌ Write SQL migration scripts
  ❌ Configure Hibernate dialect
  MongoDB creates collections automatically when you save first document.

  6. JAVA ENTITY CLASSES (MONGODB DOCUMENTS)
================================================================================

In MongoDB Spring Boot, entities use @Document instead of @Entity.
No @Table, no @Column — just plain Java class with @Document.

Example — Product.java:
────────────────────────────────────────────────────────────────────
@Document(collection = "products")
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class Product {

    @Id
    private String id;               // MongoDB ObjectId as String

    @NotBlank
    private String name;

    @NotBlank
    private String brand;

    private String category;

    @NotNull
    private Double price;

    private Double originalPrice;
    private Integer discount;
    private String description;

    @Min(0)
    private Integer stock;

    private Double rating = 0.0;
    private Integer reviewCount = 0;

    // Embedded lists — no separate table needed!
    private List<String> sizes = new ArrayList<>();
    private List<ColorOption> colors = new ArrayList<>();
    private List<ProductImage> images = new ArrayList<>();
    private List<String> tags = new ArrayList<>();

    private Boolean isFeatured = false;
    private Boolean isNew = false;
    private Boolean isBestSeller = false;
    private Boolean isActive = true;

    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}

// Embedded class (no @Document — just a nested object)
@Data
@AllArgsConstructor
@NoArgsConstructor
public class ColorOption {
    private String name;
    private String hex;
}

@Data
@AllArgsConstructor
@NoArgsConstructor
public class ProductImage {
    private String url;
    private Boolean isPrimary;
}
────────────────────────────────────────────────────────────────────

Example — User.java:
────────────────────────────────────────────────────────────────────
@Document(collection = "users")
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class User {

    @Id
    private String id;

    @NotBlank
    private String name;

    @Email
    @Indexed(unique = true)       // ensures no duplicate emails
    private String email;

    private String password;      // BCrypt hashed

    private String role = "USER"; // "USER" or "ADMIN"

    private String phone;
    private Boolean isActive = true;

    // Embedded addresses — no separate collection needed!
    private List<Address> addresses = new ArrayList<>();

    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}

@Data
@AllArgsConstructor
@NoArgsConstructor
public class Address {
    private String id;             // UUID generated manually
    private String fullName;
    private String phone;
    private String addressLine1;
    private String addressLine2;
    private String city;
    private String state;
    private String pincode;
    private Boolean isDefault = false;
}

================================================================================
  7. REPOSITORY LAYER (MongoRepository)
================================================================================

Spring Data MongoDB provides MongoRepository — works exactly like JpaRepository
but for MongoDB. No SQL needed!

Example — ProductRepository.java:
────────────────────────────────────────────────────────────────────
@Repository
public interface ProductRepository extends MongoRepository<Product, String> {

    // Spring generates the query automatically from method name!
    List<Product> findByCategory(String category);
    List<Product> findByBrand(String brand);
    List<Product> findByIsFeaturedTrue();
    List<Product> findByIsNewTrue();
    List<Product> findByIsActiveTrue();
    List<Product> findByStockLessThanEqual(int stock);

    // Custom query using @Query annotation (MongoDB JSON format)
    @Query("{ 'price': { $gte: ?0, $lte: ?1 } }")
    List<Product> findByPriceBetween(double min, double max);

    @Query("{ 'category': ?0, 'price': { $gte: ?1, $lte: ?2 } }")
    List<Product> findByCategoryAndPriceBetween(String category, double min, double max);

    // Text search (requires text index on MongoDB)
    @Query("{ $text: { $search: ?0 } }")
    List<Product> searchByText(String keyword);

    // Count by category
    long countByCategory(String category);
}
────────────────────────────────────────────────────────────────────

Example — UserRepository.java:
────────────────────────────────────────────────────────────────────
@Repository
public interface UserRepository extends MongoRepository<User, String> {
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
    List<User> findByRole(String role);
}
────────────────────────────────────────────────────────────────────

Example — OrderRepository.java:
────────────────────────────────────────────────────────────────────
@Repository
public interface OrderRepository extends MongoRepository<Order, String> {
    List<Order> findByUserIdOrderByCreatedAtDesc(String userId);
    Optional<Order> findByOrderNumber(String orderNumber);
    List<Order> findByStatus(String status);
    long countByStatus(String status);

    @Query("{ 'createdAt': { $gte: ?0, $lte: ?1 } }")
    List<Order> findByDateRange(LocalDateTime from, LocalDateTime to);
}

  10. SECURITY (SPRING SECURITY + JWT)
================================================================================

Security works EXACTLY the same as in the MySQL version.
MongoDB does not change how authentication/authorization works.

JWT Flow (same as MySQL):
  1. POST /api/auth/login with { email, password }
  2. Backend loads user from MongoDB: userRepository.findByEmail(email)
  3. BCrypt verifies password
  4. On success → generate JWT token containing userId, email, role
  5. Return token to frontend
  6. Frontend stores token, sends it in every request header
  7. JwtAuthFilter validates token on every request

Role-Based Authorization:
  @PreAuthorize("hasRole('ADMIN')")    ← Admin only endpoints
  @PreAuthorize("isAuthenticated()")   ← Any logged-in user
  (no annotation)                      ← Public endpoints

The only MongoDB-specific difference:
  UserDetailsServiceImpl.java uses UserRepository (MongoRepository)
  instead of JpaUserRepository — but the code logic is identical.

  13. WHAT CHANGES vs MYSQL VERSION
================================================================================

  Aspect               MySQL Version              MongoDB Version
  ──────────────────────────────────────────────────────────────────────────────
  pom.xml dependency   spring-boot-starter-        spring-boot-starter-
                       data-jpa + mysql-           data-mongodb
                       connector-j

  Entity annotation    @Entity                     @Document
  Table name           @Table(name="products")     @Document(collection="products")
  Column               @Column(name="...")         just field name (auto-mapped)
  Primary Key type     Long (auto-increment)       String (MongoDB ObjectId)
  Primary Key          @GeneratedValue             @Id (ObjectId auto-generated)
  Relationships        @OneToMany, @ManyToOne      Embedded documents or
                       @JoinColumn, @ForeignKey    String references (manual)
  Repository           JpaRepository<T, Long>      MongoRepository<T, String>
  Queries              JPQL / @Query with SQL       @Query with MongoDB JSON
  Schema               Fixed (need ALTER TABLE)    Flexible (just add fields)
  Migration            Flyway / Liquibase needed   NOT needed
  DB GUI               MySQL Workbench             MongoDB Compass
  Auditing             @EnableJpaAuditing          @EnableMongoAuditing
  application.props    spring.datasource.*         spring.data.mongodb.*
  Transactions         @Transactional              @Transactional (MongoDB 4+)
  Joins                Supported natively           Use $lookup aggregation
                       (LEFT JOIN, INNER JOIN)      or embed related data

  What stays the SAME:
  - Controller layer (@RestController, @GetMapping etc.) — identical
  - Service layer business logic — mostly identical
  - Security layer (JWT, Spring Security) — identical
  - DTO classes — identical
  - REST API endpoints — identical
  - Frontend JavaScript calls — identical

  14. MONGODB QUERIES IN JAVA
================================================================================

Option 1 — MongoRepository method names (auto-generated queries):
  findByCategory("football")
  findByBrandAndCategoryAndIsActiveTrue("Nike", "football")
  findByPriceBetween(1000.0, 5000.0)
  findByStockLessThanEqual(5)

Option 2 — @Query annotation with MongoDB JSON syntax:
  @Query("{ 'category': ?0, 'price': { $gte: ?1, $lte: ?2 }, 'isActive': true }")
  List<Product> findByCategoryAndPriceRange(String cat, double min, double max);

Option 3 — MongoTemplate (programmatic, most flexible):
  @Autowired
  private MongoTemplate mongoTemplate;

  // Complex product filtering example:
  public List<Product> filterProducts(String category, String brand,
                                      Double minPrice, Double maxPrice,
                                      String sortBy) {
    Query query = new Query();

    if (category != null)
        query.addCriteria(Criteria.where("category").is(category));
    if (brand != null)
        query.addCriteria(Criteria.where("brand").is(brand));
    if (minPrice != null && maxPrice != null)
        query.addCriteria(Criteria.where("price").gte(minPrice).lte(maxPrice));

    query.addCriteria(Criteria.where("isActive").is(true));

    if ("price_asc".equals(sortBy))
        query.with(Sort.by(Sort.Direction.ASC, "price"));
    else if ("price_desc".equals(sortBy))
        query.with(Sort.by(Sort.Direction.DESC, "price"));
    else if ("rating".equals(sortBy))
        query.with(Sort.by(Sort.Direction.DESC, "rating"));

    return mongoTemplate.find(query, Product.class);
  }

Option 4 — Aggregation Pipeline (for complex operations like stats):
  // Admin dashboard: total revenue
  Aggregation agg = Aggregation.newAggregation(
    Aggregation.match(Criteria.where("paymentStatus").is("PAID")),
    Aggregation.group().sum("finalAmount").as("totalRevenue")
                       .count().as("totalOrders")
  );
  AggregationResults<Map> results = mongoTemplate.aggregate(
      agg, "orders", Map.class
  );

Option 5 — Text Search (requires MongoDB text index):
  // In MongoDB, create a text index on name, brand, description, tags
  // db.products.createIndex({ name: "text", brand: "text", tags: "text" })

  @Query("{ $text: { $search: ?0 } }")
  List<Product> searchProducts(String keyword);

  15. ADMIN PANEL — MONGODB APPROACH
================================================================================

Adding a New Product (Admin → Backend → MongoDB):

  1. Admin fills product form in frontend
  2. Frontend sends POST /api/admin/products with JSON body
  3. AdminController receives ProductRequest DTO
  4. ProductService validates data, builds Product document
  5. productRepository.save(product) → MongoDB stores document
  6. New product automatically available to all users immediately

  No schema migration needed! MongoDB stores whatever fields you send.

Advantage over MySQL for admin:
  - Admin can add a new field to products (e.g. "material") without
    any database changes — just add the field to ProductRequest
    and the Product document class
  - In MySQL, you would need: ALTER TABLE products ADD COLUMN material VARCHAR(100);


Updating Product Stock After Order:
  // MongoDB update with increment operator
  mongoTemplate.updateFirst(
    Query.query(Criteria.where("id").is(productId)),
    new Update().inc("stock", -quantityOrdered),
    Product.class
  );

  16. WHEN TO CHOOSE MONGODB OVER MYSQL
================================================================================

Choose MongoDB (this document) when:
  ✅ Product data has many nested/variable fields (sizes, colors, specs)
  ✅ You want to avoid complex JOINs between tables
  ✅ Your team is comfortable with JSON-like data
  ✅ You expect to frequently add new product attributes
  ✅ You want fast horizontal scaling
  ✅ The project is a catalog/content-heavy application

Choose MySQL (previous document) when:
  ✅ You have complex financial transactions requiring full ACID compliance
  ✅ Data has very strict, fixed structure
  ✅ You need complex reporting with many table JOINs
  ✅ The team is more familiar with SQL
  ✅ You need strict referential integrity (foreign keys)

For SportZone specifically:
  Both work well. MongoDB is slightly better suited because:
  - Product variations (sizes, colors) embed naturally
  - Order history embeds item snapshots (no JOIN needed to see old data)
  - Flexible schema supports future product categories with new fields
  - Very fast product catalog reads (e-commerce's main use case)
