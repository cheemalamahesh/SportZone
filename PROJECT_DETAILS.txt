  1. PROJECT OVERVIEW
================================================================================

SportZone is a premium sports e-commerce website built entirely on the frontend
using only HTML, CSS, and JavaScript. It simulates a real-world e-commerce
platform like Amazon or Flipkart for sports goods — with no backend server,
no database, and no internet connection required after loading.

The website behaves like a Single Page Application (SPA), meaning the page
never fully reloads. Navigation happens by changing the URL hash (e.g. #/cart,
#/catalog), and JavaScript dynamically renders the correct page content.

Core Goal:
  - Look and feel like a real e-commerce website
  - Allow customers to browse, search, filter, add to cart, and checkout
  - Allow an admin to manage all products (add, edit, delete)
  - Persist all data between sessions using browser localStorage

  3. STORAGE SYSTEM
================================================================================

Storage Type: Browser localStorage
  - localStorage is a built-in browser feature
  - It stores data as key-value pairs as text (JSON format)
  - Data persists even after closing the browser tab or window
  - Data is stored locally on the user's computer
  - Nothing is sent over the internet

Keys used in localStorage:

  Key          : "sz_state"
  Contains     : Cart items, wishlist products, logged-in user info,
                 all orders, and any admin-modified products
  Format       : JSON string (parsed into a JavaScript object)

  Key          : "sz_users"
  Contains     : All registered user accounts (name, email, password)
  Format       : JSON array of user objects

  Key          : "sz_theme"
  Contains     : User's selected theme — either "dark" or "light"
  Format       : Plain string

Storage Capacity:
  - localStorage supports up to ~5MB of data per domain
  - More than sufficient for this application's needs

Important Notes:
  - Data is browser-specific (Chrome and Firefox have separate storage)
  - Clearing browser data / cache will reset all app data
  - Different devices will not share the same data
  - Opening in a different browser on the same computer = fresh data

  4. PROJECT ARCHITECTURE
================================================================================

Architecture Type: Single Page Application (SPA) with Hash-Based Routing

How it works:
  1. The browser loads index.html ONCE
  2. All JavaScript files are loaded at the start
  3. When the user clicks a link (e.g. #/catalog), the URL hash changes
  4. The Router detects the hash change via window.addEventListener('hashchange')
  5. The Router calls the correct page renderer function
  6. The page renderer writes HTML into the <main id="page-content"> element
  7. The page appears to change without any actual page reload

Pattern Used: Module Pattern
  - Each major feature (Store, Router, Navbar, etc.) is wrapped in an
    Immediately Invoked Function Expression (IIFE) and exposed as a global object
  - Example: const Store = (() => { ... return { getCart, addToCart, ... }; })();

Communication Between Modules:
  - Event-driven using a custom pub/sub system (Store.on / Store.emit)
  - When cart changes, Store emits 'cart:updated'
  - Navbar listens and re-renders the cart badge automatically

  9. HOW THE SPA (SINGLE PAGE APPLICATION) WORKS
================================================================================

Traditional Website:
  User clicks link → browser requests new HTML file from server → full page reload

SportZone SPA:
  User clicks link → URL hash changes (#/catalog) → JavaScript detects change
  → Router calls catalog renderer → Catalog HTML is injected into the page
  → No network request, no page reload, instant navigation

The Router (router.js):
  1. Registers routes: Router.register('catalog', renderCatalogPage)
  2. Listens: window.addEventListener('hashchange', resolve)
  3. Parses the URL hash to extract path and query parameters
  4. Supports dynamic segments: 'product/:id' matches '#/product/5'
  5. Calls the correct page renderer with extracted parameters
  6. Scrolls to the top of the page on every navigation

Page Rendering:
  - Each page is a JavaScript function (e.g. renderHomePage)
  - The function generates an HTML string using template literals
  - It sets document.getElementById('page-content').innerHTML = html
  - Event listeners are then attached to the newly created elements
  - This approach is called "innerHTML rendering" — no virtual DOM needed

  10. STATE MANAGEMENT & DATA FLOW
================================================================================

Central Store (store.js):
  All application state lives in a single object called "state" inside Store.
  No component directly modifies state — everything goes through Store methods.

State Object Structure:
  state = {
    cart:     [ { key, id, product, price, qty, size, color } ],
    wishlist: [ { ...productObject } ],
    user:     { name, email, role, avatar, joined } or null,
    orders:   [ { id, date, status, total, items, itemCount, address } ],
    products: [ ...productObjects ] or null (null = use seed data from data.js)
  }

How State Changes Work (Example: Add to Cart):
  1. User clicks "Add to Cart" on a product page
  2. renderProductPage() calls Store.addToCart(product, qty, size, color)
  3. Store updates state.cart
  4. Store calls localStorage.setItem('sz_state', JSON.stringify(state))
  5. Store calls emit('cart:updated', state.cart)
  6. Navbar listens via Store.on('cart:updated') and re-renders cart badge
  7. CartDrawer opens and shows the updated cart

Data Sources:
  - PRODUCTS constant (data.js) = initial seed product data
  - When admin edits products, state.products overrides the seed data
  - If state.products is null, getProducts() returns seed data
  - If state.products is an array, getProducts() returns that array

  13. WORKFLOW — HOW EVERYTHING CONNECTS
================================================================================

Startup Sequence:
  1. Browser loads index.html
  2. All 4 CSS files are applied (main, components, pages, admin)
  3. All JavaScript files load in order:
       data.js → store.js → router.js →
       toast.js → search.js → auth.js → cart-drawer.js → navbar.js →
       home.js → catalog.js → product.js → cart.js → checkout.js →
       wishlist.js → orders.js → account.js → admin.js →
       app.js (runs last, kicks everything off)
  4. app.js registers all routes with Router
  5. app.js initializes CartDrawer and Navbar
  6. app.js calls Router.init() which reads the URL hash and renders the page
  7. The footer is always visible at the bottom of index.html

Customer Shopping Workflow:
  Browse Homepage
    → Click Category or View All
    → Product Catalog (filter / sort / search)
    → Click Product Card
    → Product Detail Page
    → Select size + color + quantity
    → Click "Add to Cart"
    → Cart Drawer slides open (or go to #/cart)
    → Click Checkout
    → Login required if not signed in
    → Step 1: Fill delivery address
    → Step 2: Enter (fake) payment details
    → Step 3: Order confirmed, order ID generated
    → Order appears in #/orders

Admin Product Management Workflow:
  Login as admin@sportzone.com / Admin@123
    → Redirected to Admin Panel (#/admin)
    → Click "Products" tab
    → Click "+ Add Product"
    → Fill product form (name, price, image URL, stock, etc.)
    → Click "Add Product"
    → Product saved to localStorage
    → Product appears immediately in the storefront
    → Customer can browse and buy it

================================================================================
  17. KEY LIMITATIONS
================================================================================

Because this is a pure frontend project with no backend:

  1. PAYMENT IS FAKE
     The credit card form in checkout looks real but processes nothing.
     No actual money is charged. It is for UI demonstration only.

  2. DATA IS LOCAL
     All data (cart, orders, products, users) is stored in your browser.
     It does not sync to any server or cloud.
     If you open the site on a different device, it will be empty.

  3. PASSWORDS ARE STORED AS PLAIN TEXT
     User passwords are stored as plain text in localStorage.
     This is acceptable for a demo but NOT for a real production app.
     A real app would hash passwords and store them server-side.

  4. EMAILS ARE NOT SENT
     Order confirmation emails, welcome emails — none are actually sent.
     "Email sent" messages are simulated.

  5. IMAGES ARE FROM UNSPLASH CDN
     Product images require an internet connection to load.
     If offline, images will show as broken / empty boxes.

  6. NO REAL-TIME UPDATES
     If two browser tabs are open, changes in one tab do not
     automatically reflect in the other (until you refresh).

  7. NO SEARCH ENGINE INDEXING
     Since it is a file-based SPA, search engines (Google etc.)
     cannot index this website's content.

  8. SINGLE ADMIN
     There is only one admin account and it cannot be created or
     changed from the website interface.
