================================================================================
  1. WHAT "JAVA FULL STACK" MEANS
================================================================================

Full Stack = Frontend + Backend + Database all working together.

Current Project (Frontend Only):
  - HTML/CSS/JS runs in the browser
  - Data stored in browser localStorage (temporary, local)
  - No real security, no real payments, no real emails
  - Cannot be accessed by multiple users on different devices

Java Full Stack Project:
  Frontend  → HTML + CSS + JavaScript (React or plain JS) running in browser
  Backend   → Java Spring Boot REST API running on a server
  Database  → MySQL or PostgreSQL storing data permanently
  Server    → Tomcat (embedded in Spring Boot) serving the API

How they communicate:
  Browser (JS) ──HTTP Request──▶ Spring Boot API ──SQL Query──▶ MySQL Database
  Browser (JS) ◀──JSON Response── Spring Boot API ◀──Result──── MySQL Database

This means:
  - Any user on any device can log in and see THEIR data
  - Data is permanent (not lost when browser cache is cleared)
  - Real payments can be processed
  - Real emails can be sent
  - Admin changes affect ALL users instantly
  - Proper security with real passwords hashed (BCrypt)

  3. BACKEND TECHNOLOGY STACK
================================================================================

CORE BACKEND:
  Language          : Java 17 or Java 21 (LTS versions recommended)
  Framework         : Spring Boot 3.x
  API Type          : REST API (JSON over HTTP)
  Build Tool        : Maven (pom.xml) or Gradle (build.gradle)

DATABASE:
  Primary DB        : MySQL 8.x  OR  PostgreSQL 15.x
  ORM               : Spring Data JPA + Hibernate (maps Java classes to DB tables)
  Migration Tool    : Flyway or Liquibase (manages DB schema changes)

SECURITY:
  Authentication    : Spring Security + JWT (JSON Web Tokens)
  Password Hashing  : BCrypt (never store plain text passwords)
  Authorization     : Role-based access control (ROLE_USER, ROLE_ADMIN)

ADDITIONAL SERVICES:
  Email             : JavaMail API + Gmail SMTP  OR  SendGrid API
  File Upload       : AWS S3  OR  local file storage (Multer equivalent in Java)
  Payment           : Razorpay API  OR  Stripe API (India = Razorpay recommended)
  Caching           : Redis (for sessions, cart, frequently accessed data)

DEVELOPMENT AIDS:
  API Testing       : Postman (test your API endpoints)
  Documentation     : Springdoc OpenAPI (auto-generates Swagger UI)
  Logging           : SLF4J + Logback (built into Spring Boot)
  Validation        : Hibernate Validator / Jakarta Bean Validation

  4. BACKEND ARCHITECTURE (LAYERS)
================================================================================

Standard Layered Architecture (MVC Pattern) for Spring Boot:

  ┌─────────────────────────────────────────────────┐
  │             FRONTEND (Browser)                  │
  │    HTML + CSS + JavaScript                      │
  │    Makes HTTP calls (fetch/axios) to API        │
  └────────────────────┬────────────────────────────┘
                       │ HTTP Request (JSON)
  ┌────────────────────▼────────────────────────────┐
  │          CONTROLLER LAYER                       │
  │  @RestController classes                        │
  │  Receives HTTP requests, returns HTTP response  │
  │  Examples: ProductController, UserController    │
  └────────────────────┬────────────────────────────┘
                       │ Calls service methods
  ┌────────────────────▼────────────────────────────┐
  │           SERVICE LAYER                         │
  │  @Service classes                               │
  │  Contains business logic                        │
  │  Examples: ProductService, OrderService         │
  └────────────────────┬────────────────────────────┘
                       │ Calls repository methods
  ┌────────────────────▼────────────────────────────┐
  │         REPOSITORY LAYER                        │
  │  @Repository / JpaRepository interfaces         │
  │  Talks to the database using JPA/Hibernate      │
  │  Examples: ProductRepository, UserRepository    │
  └────────────────────┬────────────────────────────┘
                       │ SQL Queries
  ┌────────────────────▼────────────────────────────┐
  │            DATABASE (MySQL)                     │
  │  Tables: users, products, orders, cart, etc.    │
  └─────────────────────────────────────────────────┘

Additionally:
  DTOs (Data Transfer Objects) — used between Controller and Service
  Entity Classes — Java classes that map to database tables (@Entity)
  Exception Handler — Global error handling (@ControllerAdvice)
  Config Classes — Security config, CORS config, JWT config

  5. DATABASE DESIGN (TABLES & RELATIONSHIPS)
================================================================================

TABLE: users
  ──────────────────────────────────────────────────
  id            BIGINT        PRIMARY KEY AUTO_INCREMENT
  name          VARCHAR(100)  NOT NULL
  email         VARCHAR(150)  UNIQUE NOT NULL
  password      VARCHAR(255)  NOT NULL  (BCrypt hashed)
  role          ENUM          'USER', 'ADMIN'  DEFAULT 'USER'
  phone         VARCHAR(15)
  created_at    TIMESTAMP     DEFAULT CURRENT_TIMESTAMP
  updated_at    TIMESTAMP
  is_active     BOOLEAN       DEFAULT TRUE

TABLE: categories
  ──────────────────────────────────────────────────
  id            BIGINT        PRIMARY KEY AUTO_INCREMENT
  name          VARCHAR(50)   UNIQUE NOT NULL  (football, basketball, etc.)
  display_name  VARCHAR(100)
  icon          VARCHAR(10)   (emoji)
  description   TEXT

TABLE: products
  ──────────────────────────────────────────────────
  id            BIGINT        PRIMARY KEY AUTO_INCREMENT
  name          VARCHAR(200)  NOT NULL
  brand         VARCHAR(100)  NOT NULL
  category_id   BIGINT        FOREIGN KEY → categories(id)
  price         DECIMAL(10,2) NOT NULL
  original_price DECIMAL(10,2)

  description   TEXT

  is_featured   BOOLEAN       DEFAULT FALSE
  is_new        BOOLEAN       DEFAULT FALSE
  is_bestseller BOOLEAN       DEFAULT FALSE

  updated_at    TIMESTAMP

  ──────────────────────────────────────────────────
  id            BIGINT        PRIMARY KEY AUTO_INCREMENT
  product_id    BIGINT        FOREIGN KEY → products(id)

TABLE: product_colors

  ──────────────────────────────────────────────────

  8. SECURITY REQUIREMENTS (SPRING SECURITY + JWT)
================================================================================

How Authentication Works in Full Stack:

  1. User submits email + password to POST /api/auth/login
  2. Spring Security loads user from database
  3. BCrypt compares submitted password with hashed password in DB
  4. If correct → JwtUtil generates a JWT token (signed with secret key)
  5. Token returned to frontend: { token: "eyJhbG..." }
  6. Frontend stores token in localStorage or httpOnly cookie
  7. Every subsequent request sends token in header:
       Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
  8. JwtAuthFilter intercepts every request, validates the token
  9. If valid → request proceeds to controller
  10. If invalid or expired → 401 Unauthorized response

JWT Token Contents (Payload):
  {
    "sub": "user@email.com",       ← subject (email)
    "userId": 42,
    "role": "ROLE_USER",
    "iat": 1720000000,             ← issued at (timestamp)
    "exp": 1720086400              ← expires at (24 hours later)
  }

Security Rules:
  PUBLIC  (no token needed):
    GET /api/products/**
    GET /api/categories/**
    POST /api/auth/login
    POST /api/auth/register

  USER (valid token needed):
    GET/POST/DELETE /api/cart/**
    GET/POST/DELETE /api/wishlist/**
    GET/POST /api/orders/**
    GET/PUT /api/users/me/**

  ADMIN ONLY (token with ROLE_ADMIN):
    ALL /api/admin/**

Password Security:
  - Passwords are NEVER stored as plain text
  - BCrypt hashing used (automatically adds salt)
  - Example: "Admin@123" → "$2a$12$xyzABC..." (stored in DB)

  10. WHAT CHANGES IN THE FRONTEND (JAVASCRIPT)
================================================================================

The HTML and CSS stay THE SAME.
Only JavaScript needs to change — instead of localStorage, it calls the API.

Example — Current Code (localStorage):
  // store.js
  function addToCart(product, qty) {
    state.cart.push({ product, qty });
    localStorage.setItem('sz_state', JSON.stringify(state));
  }

Example — New Code (API call):
  // api.js (new file)
  async function addToCart(productId, qty, size, color) {
    const response = await fetch('http://localhost:8080/api/cart/add', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ' + getToken()   ← JWT token
      },
      body: JSON.stringify({ productId, qty, size, color })
    });
    return await response.json();
  }

Changes required in JavaScript:
  1. Add a new api.js file with fetch() calls for every feature
  2. Store JWT token in localStorage after login
  3. Send token in Authorization header on every request
  4. Handle 401 responses (redirect to login)
  5. Remove all direct localStorage reads for cart/orders/wishlist
  6. Add loading states for API calls (they take time, unlike localStorage)
  7. Add error handling for network failures

Alternatively: Replace plain JS with React.js for better API handling.
  React would use Axios library for HTTP calls and Redux/Context for state.

  12. PAYMENT GATEWAY INTEGRATION
================================================================================

Recommended for India: Razorpay
Recommended for International: Stripe

Razorpay Integration Flow:
  1. Customer clicks "Place Order"
  2. Frontend calls POST /api/payment/create-order
  3. Backend creates a Razorpay Order ID using Razorpay Java SDK
  4. Razorpay Order ID returned to frontend
  5. Frontend opens Razorpay payment popup (using Razorpay JS SDK)
  6. Customer enters card / UPI / net banking details
  7. Payment processed by Razorpay
  8. On success, Razorpay returns payment_id + signature
  9. Frontend sends POST /api/payment/verify with payment_id + signature
  10. Backend verifies the signature (HMAC SHA256) with Razorpay secret
  11. If verified → order confirmed, stock reduced, email sent
  12. If not verified → order failed, money auto-refunded by Razorpay

Supported Payment Methods via Razorpay:
  - Credit / Debit Cards (Visa, Mastercard, RuPay)
  - UPI (Google Pay, PhonePe, Paytm, etc.)
  - Net Banking (all major banks)
  - EMI
  - Wallets (Paytm, Amazon Pay)

  14. FILE / IMAGE UPLOAD REQUIREMENTS

Current Setup: Product images are Unsplash URLs (external links).

Full Stack Setup: Admin uploads actual image files.

Flow:
  Admin selects image file → multipart/form-data POST to /api/admin/upload/image
  Backend receives MultipartFile → saves to storage → returns URL

Storage Options:

  Option 1: AWS S3 (Recommended for production)
    - Create S3 bucket in AWS console
    - Configure bucket for public read access
    - Use AWS SDK in Java to upload
    - Image URL: https://sportzone-images.s3.ap-south-1.amazonaws.com/products/abc.jpg
    - Cost: ~$0.023 per GB stored + $0.09 per GB transferred

  Option 2: Local Server Storage (for development)
    - Save files to /uploads/products/ folder on server
    - Serve via Spring Boot static resource mapping
    - Image URL: http://localhost:8080/uploads/products/abc.jpg
    - NOT suitable for production (no CDN, no backup)

  Option 3: Cloudinary (free tier available)
    - Free: 25 credits/month (enough for development)
    - Automatic image optimization and CDN delivery
    - Java SDK available

Validation:
  - Max file size: 5MB
  - Allowed types: jpg, jpeg, png, webp
  - Auto-resize to product card dimensions (400x400 recommended)
